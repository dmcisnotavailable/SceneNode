# SceneNote v0.6｜视频处理任务编排优化实验报告

## 1. 背景与优化目标

SceneNote 是一个基于 AI 的长视频理解与片段检索工具。用户上传视频后，系统依次完成音频提取、语音转写、视频抽帧、视觉理解、多模态融合和章节生成。

初版采用完全串行的 Pipeline：

```text
视频上传
   ↓
FFmpeg 音频提取
   ↓
Whisper 语音转写
   ↓
FFmpeg 视频抽帧
   ↓
视觉模型逐帧分析
   ↓
多模态时间轴融合
   ↓
LLM 章节生成
```

在 v0.6 的初始性能测试中，后台完整分析耗时 166.349 秒。其中 Whisper 初始化与推理耗时占约 49.8%，是最主要的性能瓶颈。

针对这一问题，v0.6 分两部分优化：

- **模型推理优化**：调整 Whisper 解码参数、复用模型实例，减少 ASR 处理时间。
- **任务编排优化**：分析各处理阶段的数据依赖，引入视觉 API 有界并发与 ASR/视觉双分支并行，减少不必要的串行等待。

本文重点记录第二部分的设计、实现与实验结果。

## 2. 任务依赖分析与架构改造

### 2.1 原始架构的问题

原始 Pipeline 中，视觉处理必须等待 Whisper 转写完成后才会开始。

但从数据依赖关系来看：

- ASR 分支仅依赖视频中的音频。
- 视觉分支仅依赖视频画面。
- 多模态融合依赖两个分支的处理结果。
- 章节生成依赖融合后的时间轴。

因此，ASR 与视觉分析不存在直接的数据依赖，可以并行执行。

原来的线性处理方式增加了不必要的等待时间。

### 2.2 优化后的任务编排

```text
                  视频上传
                     |
          +----------+----------+
          |                     |
      ASR 分支               视觉分支
          |                     |
     FFmpeg 提取音频        FFmpeg 抽帧
          |                     |
     Whisper 转写          视觉 API 并发
          |                     |
          +----------+----------+
                     |
              等待两路完成
                     |
              多模态时间轴融合
                     |
                LLM 章节生成
                     |
                 保存结果
```

通过 `ThreadPoolExecutor(max_workers=2)` 同时提交 ASR 和视觉任务，并通过 `Future.result()` 等待两路完成后再进行融合。

对于原本串行的两个独立任务，理论上：

```text
串行耗时 ≈ T_ASR + T_Vision

并行耗时 ≈ max(T_ASR, T_Vision) + 调度开销
```

但实际收益还会受到 CPU、磁盘 I/O、网络和远程模型服务负载的影响。

因此，**并行化只是候选优化方案，是否采用需要通过端到端性能测试验证。**

## 3. 关键工程改动

### 3.1 视觉 API 有界并发

**修改文件：`backend/describe_frames.py`**

原实现对六张采样帧逐张调用视觉模型，必须等待当前请求完成后才能发送下一张图片。

优化后：

- 使用 `ThreadPoolExecutor` 限制同时执行的视觉请求数。
- 使用 `as_completed()` 按完成顺序收集结果。
- 由主线程统一保存成功结果，避免多个线程同时写入缓存。
- 按原视频时间戳排序，避免并发完成顺序影响后续融合。
- 保留逐帧缓存和异常收集，降低失败后的重复调用成本。

并发数通过 `VISION_WORKERS` 配置，默认候选为 2。

这里选择线程池主要是因为视觉分析涉及远程 API 调用，等待网络响应期间可以执行其他请求。采用有限并发而非无限并发，是为了控制第三方 API 限流和请求资源消耗。

### 3.2 ASR 与视觉双分支并行

**修改文件：`backend/pipeline.py`**

将原本串行的音频处理和视觉处理封装为两个独立函数：

- `run_audio_branch()`：音轨检测、音频提取、Whisper 转写。
- `run_visual_branch()`：视频抽帧、视觉模型分析。

通过线程池同时提交两个分支，等待两路结果后再执行多模态融合和章节生成。

这种设计将原来的线性 Pipeline 改造成具有明确依赖关系的 DAG，既减少独立任务间的等待，又保留融合阶段的数据完整性要求。

### 3.3 并发状态与性能指标管理

并行化后，需要避免两个分支同时修改共享状态。

本次采用：

- ASR 与视觉分支分别收集性能指标。
- 主线程在两个 Future 完成后统一合并指标。
- 主流程统一更新 `status.json` 中的任务阶段，避免两个分支交替覆盖前端状态。
- 使用 `time.perf_counter()` 记录各阶段 Wall Time，保存到 `performance.json`。

对于单分支异常，保留降级处理机制，同时记录警告，避免将部分能力失败误认为完整成功。

### 3.4 可配置的执行策略

为便于隔离不同优化措施的影响，在 `pipeline.py` 中增加两个环境变量：

| 配置 | 作用 |
|---|---|
| `PIPELINE_PARALLEL` | 控制 ASR 与视觉分支是否并行 |
| `VISION_WORKERS` | 控制视觉 API 的最大并发数 |

通过配置切换不同执行策略，而不需要反复修改核心业务代码。

## 4. 对照实验设计

### 4.1 实验目标

分别验证两个问题：

1. 视觉 API 从串行改为双并发，是否能降低视觉分析和端到端处理耗时？
2. 在视觉双并发的基础上，进一步开启 ASR/视觉双分支并行，是否能继续缩短总处理时间？

### 4.2 实验分组

| 组别 | PIPELINE_PARALLEL | VISION_WORKERS | 执行策略 |
|---|---|---|---|
| A | 0 | 1 | 完全串行 |
| B2 | 0 | 2 | 视觉 API 双并发，流水线串行 |
| C | 1 | 2 | ASR/视觉双分支并行，视觉 API 双并发 |

三组使用相同测试视频和 Whisper 参数，每次上传生成独立任务目录，避免复用已有视觉结果。

Whisper 采用 `small + CPU + int8 + beam_size=1 + VAD` 配置。

本次主要比较后台 `process_video()` 的 Wall Time，不包含浏览器上传耗时。

### 4.3 实验异常与修正

首次 A/B/C 测试中，视觉分支因 `describe_frames()` 函数签名与调用参数不一致而抛出 `TypeError`。

由于 Pipeline 支持单分支降级，任务仍然生成了章节，但视觉分析实际没有执行。因此首次测试数据被排除，修复后重新进行完整多模态测试。

第二次 B 组测试期间，另一个视频触发语义搜索，并加载多语言 Embedding 模型，耗时约 24 秒。该操作与 Whisper 推理时间重叠，可能引入额外 CPU、内存及磁盘资源竞争。

因此保留原始 B 组日志作为异常实验记录，重新执行无该干扰的 B2 测试。

最终使用 A、B2、C 三组数据进行对照。

## 5. 实验结果

### 5.1 端到端性能对比

| 指标 | A：完全串行 | B2：视觉双并发 | C：双分支并行 |
|---|---:|---:|---:|
| 音视频处理阶段 | 71.425s | 62.059s | 50.980s |
| Whisper 初始化 | 10.663s | 8.206s | 18.272s |
| Whisper 推理 | 21.340s | 22.367s | 30.204s |
| FFmpeg 抽帧 | 9.793s | 9.461s | 17.135s |
| 视觉 API | 28.069s | 20.519s | 33.137s |
| LLM 章节生成 | 10.832s | 10.001s | 22.371s |
| **后台总耗时** | **82.308s** | **72.131s** | **73.593s** |

耗时降低率计算方式：

```text
耗时降低率 = (优化前耗时 - 优化后耗时) / 优化前耗时 × 100%
```

三组对照结果：

| 对比 | 总耗时变化 | 耗时降低率 |
|---|---|---:|
| A → B2 | 82.308s → 72.131s | **12.36%** |
| B2 → C | 72.131s → 73.593s | **-2.03%** |
| A → C | 82.308s → 73.593s | **10.59%** |

### 5.2 视觉 API 并发收益

对比 A 与 B2，视觉分析耗时从 28.069 秒下降至 20.519 秒：

```text
(28.069 - 20.519) / 28.069 × 100%
= 26.9%
```

六帧视觉分析节省约 7.55 秒。

与此同时，Whisper 推理耗时分别为 21.340 秒和 22.367 秒，差异相对较小。

**实验观察：视觉 API 双并发能够减少远程请求的串行等待，并在本轮测试中带来约 12.4% 的端到端耗时改善。**

### 5.3 双分支并行收益

对比 B2 与 C，音视频处理阶段从 62.059 秒下降至 50.980 秒：

```text
(62.059 - 50.980) / 62.059 × 100%
= 17.9%
```

这说明通过重叠执行 ASR 和视觉任务，核心处理阶段的 Wall Time 得到改善。

但后台总耗时却从 72.131 秒增加至 73.593 秒，增加约 2.0%。

进一步分析发现，C 组多个阶段出现耗时增长：

| 阶段 | B2 | C | 增量 |
|---|---:|---:|---:|
| Whisper 初始化 | 8.206s | 18.272s | +10.066s |
| Whisper 推理 | 22.367s | 30.204s | +7.837s |
| FFmpeg 抽帧 | 9.461s | 17.135s | +7.674s |
| 视觉 API | 20.519s | 33.137s | +12.618s |
| LLM 章节生成 | 10.001s | 22.371s | +12.370s |

尽管双分支并行减少了串行等待，但局部耗时增加抵消了部分收益。

## 6. 性能分析与技术取舍

### 6.1 为什么并发增加不一定更快？

并行执行降低的是任务之间的等待时间，并不意味着每个任务自身的执行时间也会降低。

在当前单机 CPU 环境下，可能存在：

- Whisper 与 FFmpeg 抽帧竞争 CPU 资源。
- 多个媒体处理任务竞争磁盘 I/O。
- 视觉 API 受网络波动、远程服务排队或限流影响。
- LLM 章节生成存在独立的远程响应延迟波动。

本次 C 组 Whisper 和 FFmpeg 的耗时增长与资源竞争的可能表现一致，但尚未采集 CPU、内存及磁盘利用率数据，不能直接证明因果关系。

尤其是视觉 API 和 LLM 的耗时变化，也可能来自远程模型服务的负载波动。

### 6.2 为什么不直接默认开启双分支并行？

本轮测试中：

- B2 的后台总耗时最低，为 72.131 秒。
- C 的核心音视频处理阶段最快，为 50.980 秒。
- C 的后台总耗时反而比 B2 增加约 2.0%。

SceneNote 当前主要优化目标是**用户从上传完成到拿到章节结果的等待时间**，因此端到端耗时比单个阶段的执行时间更重要。

综合当前单轮实验，暂时将“视觉双并发 + ASR/视觉串行”作为单机默认候选方案：

```powershell
$env:PIPELINE_PARALLEL="0"
$env:VISION_WORKERS="2"
```

保留双分支并行模式作为可切换实验方案：

```powershell
$env:PIPELINE_PARALLEL="1"
$env:VISION_WORKERS="2"
```

这一决策不是认为双分支并行无效，而是当前证据尚不足以证明它能够稳定降低端到端延迟。

### 6.3 实验局限

当前实验仍存在以下限制：

1. 每种模式只有一轮有效测试，尚未获得稳定的中位数和波动范围。
2. Whisper 模型初始化和推理耗时在不同运行间存在波动。
3. 视觉 API 与章节 LLM 依赖远程服务，响应时间不可完全控制。
4. 尚未记录 CPU、内存、磁盘 I/O 和模型 API 的完整资源指标。
5. 尚未对不同视频长度、不同语言和复杂场景进行系统评测。

因此，本文中的性能提升数字均表示**当前测试条件下的观察结果**，而非生产环境的稳定性能保证。

## 7. 工程总结

本次优化遵循了以下过程：

```text
发现视频处理缓慢
        ↓
增加阶段级性能埋点
        ↓
定位 Whisper 推理瓶颈
        ↓
优化模型参数与加载方式
        ↓
分析 ASR/视觉任务依赖
        ↓
引入视觉 API 有界并发
        ↓
引入双分支并行执行
        ↓
处理共享状态、结果排序与异常降级
        ↓
设计 A/B/C 对照实验
        ↓
定位接口错误和测试干扰
        ↓
比较局部收益与端到端收益
        ↓
基于实测结果选择执行策略
```

本次实验最重要的结论是：

**并发优化的目标不是最大化线程数量，而是在保证结果正确性的前提下，最小化用户实际等待的端到端时间。**

同时，性能优化不能只关注单个模块的耗时，还需要结合整体执行链路、资源竞争、异常状态和实验条件进行综合判断。

## 8. 后续优化方向

- 重复执行多轮 A/B/C 实验，统计中位数和 P95 耗时。
- 增加 CPU、内存、磁盘 I/O 和远程 API 延迟监控。
- 进一步研究 FFmpeg 抽帧与 Whisper 推理的资源隔离。
- 引入任务状态持久化、Checkpoint 与失败恢复，避免高成本阶段重复计算。
- 建立章节生成与视频片段定位的质量回归测试集。
